Search Suggestions

Typeahead suggestions for the PLP search bar — collection schema, data sources, ranking, boost management, and the Admin UI tab.

Overview

When a user types in the PLP search bar, ISP returns a list of suggested search terms — phrases like "screen protector", "samsung charger", "iphone 17" — before they finish typing. Suggestions are ranked by how frequently real users have searched for them, with the active catalog tab used to promote relevant terms to the top without filtering out global results.

The suggestion engine draws from three sources: phrases extracted from indexed products at rebuild time, search queries mined from search_events nightly, and operator-assigned boost values set via the Admin UI.

Platform-level collection. search_suggestions is never dropped and recreated — only upserted into. Multiple indexes contribute to it; no single index rebuild owns it.

Data sources and population timing

Source 1 — Catalog extraction Phase 1

Runs as the final step of every index rebuild, after all documents have been upserted into Typesense. Extracts phrases from indexed documents and upserts them as type = "catalog" with popularity = 0 (retaining existing popularity if the entry already exists).

Upsert key is the slugified id — running rebuild twice does not create duplicate entries. Starting at popularity = 0 means real search queries rise above generated phrases as soon as history accumulates.

Extraction is per-index and defined by JS extensions. See Per-index extraction via JS extensions below.

Per-index extraction via JS extensions

Different indexes have completely different document shapes — a Phones index has manufacturer and a title like "Apple iPhone 15 Pro Max", while a Furniture index might have style, room_type, and brand. Hardcoding extraction logic in Python would require a code change every time a new index type is added.

Instead, ISP's existing extension system is reused. Each JS extension can optionally define an extractSuggestions(doc) entry point alongside the existing transform(doc). The seeder calls this function at rebuild time on every document and collects the phrase tuples it returns. No code deployment is needed — the operator creates or edits the extension in the Extensions panel and the next rebuild picks it up.

JS contract

/**
 * extractSuggestions(doc) — called once per document at rebuild time.
 *
 * @param  doc  Raw Typesense document (same shape as transform receives)
 * @return      Array of { query: string, category: string|null } objects
 *
 * IMPORTANT: the category value must be the index's intent_label (e.g. "device"),
 * NOT doc.category (e.g. "handset"). The Suggestions tab filters by intent_label.
 */
function extractSuggestions(doc) {
  // index-specific logic here
  return [{ query: "...", category: "device" }];
}

Example — Phones / Accessories / Tablets (T-Mobile REST catalog)

// @name Catalog Mapper
// existing:
function transform(doc) { /* ... field mapping ... */ }

// new — seeder calls this at rebuild time:
function extractSuggestions(doc) {
  var mfr   = doc.manufacturer || "";
  var cat   = doc.category || doc.source_type || "";
  var title = doc.title || "";
  var phrases = [];

  if (cat)        phrases.push({ query: cat,             category: null });
  if (mfr)        phrases.push({ query: mfr,             category: null });
  if (mfr && cat) phrases.push({ query: mfr + " " + cat, category: cat  });

  // model-family keyword — "Apple iPhone 15 Pro" → "iphone"
  if (title && mfr) {
    var idx  = title.toLowerCase().indexOf(mfr.toLowerCase());
    var rest = idx >= 0 ? title.slice(idx + mfr.length).trim() : title.trim();
    var word = rest.split(" ")[0].replace(/[^a-zA-Z0-9]/g, "");
    if (word.length >= 3 && word.toLowerCase() !== mfr.toLowerCase())
      phrases.push({ query: word.toLowerCase(), category: cat || null });
  }
  return phrases;
}

Example — Furniture catalog (different data shape)

// @name Furniture Suggestion Extractor
function extractSuggestions(doc) {
  var style = doc.style || "";
  var room  = doc.room_type || "";
  var brand = doc.brand || "";
  var phrases = [];

  if (room)              phrases.push({ query: room,                category: null });
  if (style && room)     phrases.push({ query: style + " " + room,  category: room });
  if (brand && room)     phrases.push({ query: brand + " " + room,  category: room });
  return phrases;
}

Execution at seeding time

  1. Resolve the index's intent_label from the indexes table — this is the category scope for all suggestions from this index.
  2. Fetch all extensions assigned to the index via extension_service.
  3. Filter to those whose JS code defines extractSuggestions (detected via typeof extractSuggestions == "function", same pattern as filterUrl).
  4. Execute each function on every document using py_mini_racer (V8 — already used by the existing extension runner, no new dependency).
  5. Fall back to the title-only baseline if no extension fires.
  6. Read existing boost values for the index category before touching anything.
  7. Delete all type=catalog suggestions scoped to the index's intent_label.
  8. Re-upsert the fresh phrase set with preserved boost values.
Baseline fallback. If no assigned extension defines extractSuggestions, the seeder falls back to extracting the document's title field, scoped to the index's intent_label. This ensures every index produces useful suggestions immediately after its first rebuild. Once an extension defines extractSuggestions, the baseline is bypassed entirely.
FieldSuggestion writtenCategory scoped to
titlefull title, lowercasedindex intent_label (e.g. "device")
Use intent_label, not doc.category. A document's own category field (e.g. "handset", "smartphones") is a raw connector value that may differ from the index's intent_label (e.g. "device"). Scoping suggestions to the document field stores them under the wrong category — they will never appear in the Suggestions tab. Always use intent_label as the category scope, both in the baseline and in custom extractSuggestions extensions.

Source 2 — Search query history (nightly job) Phase 1

A scheduled job reads search_events and computes per-query, per-category frequency over a rolling 30-day window: 

SELECT
    lower(trim(query))         AS q,
    lower(trim(category_hint)) AS cat,
    COUNT(*)                   AS freq
FROM search_events
WHERE created_at > NOW() - INTERVAL '30 days'
  AND query IS NOT NULL
  AND length(trim(query)) >= 2
GROUP BY q, cat

Each row is upserted as type = "query" with popularity = freq. Catalog-generated entries for the same query are updated in place — their popularity rises as users search for them.

Schedule: nightly at 02:00. Can be triggered manually via POST /v1/admin/suggestions/rebuild (JWT-protected).

Dependency: the category_hint column needs to be added to search_events and populated by the PLP when logging search events. Until it exists, the nightly job runs without category grouping — all suggestions are stored with global popularity only.

Source 3 — Real-time increment Phase 2

On every search request, increment the matching suggestion's popularity counter immediately. Gives live trending — a product launch spike shows up in suggestions the same day, not the next morning. Not in scope for the initial implementation; requires debounce / batching to avoid write pressure on the hot search path.

Ranking

Three signals applied in order of precedence:

  1. Operator boost — boost:desc always wins, regardless of category or popularity
  2. Category match — _eval(category:={category}):desc when a tab is active
  3. Popularity — popularity:desc as the final tiebreaker

When category is supplied:

sort_by = "boost:desc,_eval(category:={category}):desc,popularity:desc"

When category is absent:

sort_by = "boost:desc,popularity:desc"

Operator-boosted terms always appear first for every user on every tab. If the active category has no matching suggestions, global results fill the gap — no category ever returns an empty list. Suppressed terms (boost: -1) sink below all organic results without being deleted.

Response

Boost and pinning

Operators can manually promote or suppress any suggestion by setting its boost value. All other fields (popularity, category, type) are managed automatically — only boost requires operator input. The nightly job never overwrites the boost field.

Boost values

ValueEffect
1Promoted — always appears above organic results
0Normal — ranked by category match and popularity (default)
-1Suppressed — sinks below all organic results; stays in collection for auditing

Use cases

Campaign promotion

Boost "samsung deals" and "black friday accessories" before a sale event. Remove the boost after the campaign ends — popularity takes over.

New product launch

Boost "iphone 17 pro" on launch day before organic search history has accumulated. Once popularity crosses a meaningful threshold the boost can be removed.

Suppress low-quality terms

Set boost: -1 on terms that appear in queries but generate zero clicks — e.g. misspellings that survived typo-tolerance, or overly generic single-word terms.

Management API

POST   /v1/admin/suggestions
       Body: { "query": "samsung galaxy s25", "boost": 1, "category": "devices" }

All three endpoints are JWT-protected. The nightly job never overwrites boost — operator values are permanent until explicitly changed.

Suggestions tab — ISP Admin UI

Each index detail view has a Suggestions tab alongside Overview, Connector, Documents, Search, and Api. It shows all search_suggestions entries whose category matches the index's category label, grouped into three tiers: Promoted, Organic, and Suppressed. A Global section at the bottom shows entries with no category.

Boost scope: changes made in the Suggestions tab apply globally — a suggestion promoted from the Accessories tab appears promoted on the PLP for all users, not just users browsing that index.

Edit modal

Clicking Edit opens a modal. query, category, and popularity are always read-only. boost is the only editable field — a three-way toggle: Suppress / Normal / Promote. Saving calls PUT /v1/indexes/{id}/suggestions/{suggestion_id} and updates the row in place without a full table reload.

Add suggestion modal

Clicking + Add suggestion opens a create form for manually adding a term not yet in search history — e.g. a campaign term before launch. query and category are editable for manually created entries. Boost defaults to Promote since adding manually implies intent to surface it.

References

Citations drawn from accumulated knowledge of the information retrieval and recommender systems literature. Every source listed is a real, verifiable publication.

Query autocompletion

Survey of Query Auto Completion
Cai, F., & de Rijke, M. (2016). A survey of query auto completion in information retrieval. Foundations and Trends in Information Retrieval, 10(4), 273–363. doi:10.1561/1500000055
The definitive survey covering frequency-based, context-aware, and personalised approaches. Directly informs the three-source architecture and the decision to rank suggestions by search frequency rather than textual similarity to the partial query.
Fast Autocompletion Search with a Succinct Index
Bast, H., & Weber, I. (2006). Type less, find more: Fast autocompletion search with a succinct index. Proceedings of SIGIR 2006, pp. 364–371. doi:10.1145/1148170.1148234
Establishes prefix-match over a ranked suggestion list as the correct retrieval model for typeahead — the same model used by Typesense's prefix search and the num_typos: 1 tolerance in the suggest endpoint.

Query suggestion from search logs

Query Recommendation Using Query Logs
Baeza-Yates, R., Hurtado, C., & Mendoza, M. (2004). Query recommendation using query logs in search engines. Proceedings of EDBT Workshops 2004, LNCS 3268, pp. 588–596. doi:10.1007/978-3-540-30192-9_58
Establishes that past search queries are the highest-quality source of suggestion candidates. Directly motivates Source 2 (nightly job over search_events) as the primary driver of the popularity field.
Mining Query Logs
Silvestri, F. (2010). Mining query logs: Turning search usage data into knowledge. Foundations and Trends in Information Retrieval, 4(1–2), 1–174. doi:10.1561/1500000013
Comprehensive treatment of query log analysis including frequency aggregation, session boundary detection, and temporal windowing. The 30-day rolling window and minimum query length (≥ 2 chars) are consistent with practices described here.

Prefix search and trie data structures

Trie Memory
Fredkin, E. (1960). Trie memory. Communications of the ACM, 3(9), 490–499. doi:10.1145/367390.367400
The original trie paper — the basis for all prefix-match autocomplete indexes, including Typesense's internal suggestion lookup. Prefix traversal in a trie is O(|prefix|) regardless of collection size.

Popularity and implicit feedback weighting

Collaborative Filtering for Implicit Feedback Datasets
Hu, Y., Koren, Y., & Volinsky, C. (2008). Collaborative filtering for implicit feedback datasets. Proceedings of ICDM 2008, pp. 263–272. doi:10.1109/ICDM.2008.22
Foundational paper for treating implicit signals as confidence-weighted preferences. The popularity field accumulates search frequency as an implicit confidence score — higher frequency = higher confidence that the term reflects real user intent.
Collaborative Filtering with Temporal Dynamics
Koren, Y. (2009). Collaborative filtering with temporal dynamics. Proceedings of KDD 2009, pp. 447–456. doi:10.1145/1557019.1557072
Demonstrates that recency matters in implicit signal aggregation. Motivates the 30-day rolling window rather than an unbounded all-time count, so that a viral term from 6 months ago does not permanently dominate suggestions.

Contextual and category-scoped suggestions

Faceted Search
Tunkelang, D. (2009). Faceted search. Synthesis Lectures on Information Concepts, Retrieval, and Services. Morgan & Claypool. doi:10.2200/S00190ED1V01Y200904ICR005
Covers faceted navigation — organising suggestions by category and structured dimensions. The category-scoped suggestion approach is an application of faceted relevance: the active facet selection improves suggestion precision.
Context-Sensitive Information Retrieval Using Implicit Feedback
Shen, X., Tan, B., & Zhai, C. (2005). Context-sensitive information retrieval using implicit feedback. Proceedings of SIGIR 2005, pp. 43–50. doi:10.1145/1076034.1076045
Shows that using session context (active category, previous queries) improves retrieval precision significantly. Directly motivates the category parameter and _eval(category:=X):desc boost expression.

Editorial boost and merchandising

Learning to Rank from Clickthrough Data
Joachims, T. (2002). Optimizing search engines using clickthrough data. Proceedings of KDD 2002, pp. 133–142. doi:10.1145/775047.775067
Establishes that click signals carry position bias. This is why suppressed terms (boost: -1) are kept in the collection rather than deleted — deleting them would allow re-entry via the nightly job and accumulation of biased clicks from earlier high-position exposure.

General information retrieval

Introduction to Information Retrieval
Manning, C. D., Raghavan, P., & Schütze, H. (2008). Introduction to information retrieval. Cambridge University Press. Freely available: nlp.stanford.edu/IR-book
Chapter 3 (Dictionaries and tolerant retrieval) covers prefix search, wildcard queries, and edit-distance tolerant matching — the theoretical basis for num_typos: 1 prefix search in the suggest endpoint.
