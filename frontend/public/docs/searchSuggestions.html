Search Suggestions

Typeahead suggestions for the PLP search bar — collection schema, data sources, ranking, boost management, link mode with auto-pin, and the Admin UI tab.

Overview

When a user types in the PLP search bar, ISP returns a list of suggested search terms — phrases like "screen protector", "samsung charger", "iphone 17" — before they finish typing. Suggestions are ranked by how frequently real users have searched for them, with the active catalog tab used to promote relevant terms to the top without filtering out global results.

The suggestion engine draws from three sources: phrases extracted from indexed products at rebuild time, search queries mined from search_events nightly, and operator-assigned boost values set via the Admin UI.

Platform-level collection. search_suggestions is never dropped and recreated — only upserted into. Multiple indexes contribute to it; no single index rebuild owns it.

Data sources and population timing

Source 1 — Catalog extraction Phase 1

Runs as the final step of every index rebuild, after all documents have been upserted into Typesense. Extracts phrases from indexed documents and upserts them as type = "catalog" with popularity = 0 (retaining existing popularity if the entry already exists).

Upsert key is the slugified id — running rebuild twice does not create duplicate entries. Starting at popularity = 0 means real search queries rise above generated phrases as soon as history accumulates.

Extraction is per-index and defined by JS extensions. See Per-index extraction via JS extensions below.

Per-index extraction via JS extensions

Different indexes have completely different document shapes — a Phones index has manufacturer and a title like "Apple iPhone 15 Pro Max", while a Furniture index might have style, room_type, and brand. Hardcoding extraction logic in Python would require a code change every time a new index type is added.

Instead, ISP's existing extension system is reused. Each JS extension can optionally define an extractSuggestions(doc) entry point alongside the existing transform(doc). The seeder calls this function at rebuild time on every document and collects the phrase tuples it returns. No code deployment is needed — the operator creates or edits the extension in the Extensions panel and the next rebuild picks it up.

JS contract

/**
 * extractSuggestions(doc) — called once per document at rebuild time.
 *
 * @param  doc  ISP catalog document already mapped to the Typesense schema.
 *              Not the raw API payload — fields like title, manufacturer,
 *              operating_system, price, and metadata (JSON string) are available.
 * @return      Array of { query, category?, url?, doc_id? } objects.
 *              - category: optional — when omitted the seeder uses the index's
 *                intent_label automatically.
 *              - url: optional — when present, seeder sets mode = "link" so the
 *                PLP navigates directly to the URL rather than running a search.
 *              - doc_id: optional — when present, seeder stores it in
 *                featured_doc_ids so that doc is pinned at position #1 for
 *                search-mode suggestions.
 */
function extractSuggestions(doc) {
  // index-specific logic here
  return [{ query: "..." }];   // category omitted → seeder uses intent_label
}
category is optional. When omitted or null, the seeder automatically scopes the suggestion to the index's intent_label (read from the indexes table). A single extension can therefore be assigned to Phones, Tablets, and Smartwatches without knowing or hardcoding the category string.

Example — Device catalog (backend/extensions/device_suggestions.js)

The real extension currently assigned to the Phones index. Reusable for Tablets and Smartwatches — category is omitted so the seeder infers it from each index's intent_label.

Extracts only the product title and aliases — simple and reliable. Richer phrases (brand combos, OS, price tier) are added organically as real user searches accumulate via the nightly aggregation job.

// @name Device Suggestions
// @description Generates typeahead search suggestions from ISP catalog device documents.
// Assign to Phones, Tablets, or Smartwatches indexes.

function extractSuggestions(doc) {
  var results = [];
  var seen = {};

  function add(query) {
    var q = String(query || '').trim().toLowerCase();
    if (q && !seen[q]) { seen[q] = true; results.push({ query: q }); }
  }

  add(doc.title);

  var meta = {};
  try { meta = JSON.parse(doc.metadata || '{}'); } catch (e) {}
  (meta.aliases || []).forEach(function(a) { add(a); });

  return results;
}

Example — Furniture catalog (different data shape)

// @name Furniture Suggestion Extractor
function extractSuggestions(doc) {
  var style = doc.style || "";
  var room  = doc.room_type || "";
  var brand = doc.brand || "";
  var phrases = [];

  if (room)          phrases.push({ query: room });
  if (style && room) phrases.push({ query: style + " " + room });
  if (brand && room) phrases.push({ query: brand + " " + room });
  return phrases;
}

Execution at seeding time

Python (suggestion_service.py) is pure orchestration — no phrase logic lives here:

  1. Fetch all documents from the index's Typesense collection (paginated, 250/page).
  2. Resolve the index's intent_label from the indexes table.
  3. Load assigned extensions and filter to those that define extractSuggestions (detected via typeof extractSuggestions == "function").
  4. Execute each function on every document using py_mini_racer (V8). If no extension defines extractSuggestions, seeding stops here — nothing is upserted.
  5. For each returned phrase: if category is omitted or null, substitute intent_label so the suggestion is correctly scoped.
  6. Read existing boost values for the index category before touching anything.
  7. Delete stale type=catalog entries by both intent_label and any raw document category slugs (catches legacy entries from older extractors).
  8. Re-upsert the fresh phrase set with preserved boost values.
No Python fallback. If an index has no extension with extractSuggestions, that index produces no catalog suggestions. All phrase decisions live in JS — Python only orchestrates fetch, run, and upsert.
If you set category explicitly: use intent_label, not doc.category. A document's own category field (e.g. "handset", "smartphones") is a raw connector value that may differ from the index's intent_label (e.g. "device"). Scoping suggestions to the document field stores them under the wrong category — they will never appear in the Suggestions tab. The safest approach is to omit category entirely and let the seeder fill in intent_label automatically.

Source 2 — Search query history (nightly job) Phase 1

A scheduled job reads search_events and computes per-query, per-category frequency over a rolling 30-day window: 

SELECT
    lower(trim(query))         AS q,
    lower(trim(category_hint)) AS cat,
    COUNT(*)                   AS freq
FROM search_events
WHERE created_at > NOW() - INTERVAL '30 days'
  AND query IS NOT NULL
  AND length(trim(query)) >= 2
GROUP BY q, cat

Each row is upserted as type = "query" with popularity = freq. Catalog-generated entries for the same query are updated in place — their popularity rises as users search for them.

Schedule: nightly at 02:00. Can be triggered manually via POST /v1/admin/suggestions/rebuild (JWT-protected).

To re-seed catalog suggestions for a single index without a full data rebuild (e.g. after assigning or editing an extractSuggestions extension): 

POST /v1/admin/suggestions/seed/{index_id}

Runs the same 9-step refresh as the post-rebuild hook — reads existing Typesense documents, runs JS extractors, preserves boost, deletes stale entries, re-upserts — without touching connector config or re-fetching from the source API.

Dependency: the category_hint column needs to be added to search_events and populated by the PLP when logging search events. Until it exists, the nightly job runs without category grouping — all suggestions are stored with global popularity only.

Source 3 — Real-time increment Phase 2

On every search request, increment the matching suggestion's popularity counter immediately. Gives live trending — a product launch spike shows up in suggestions the same day, not the next morning. Not in scope for the initial implementation; requires debounce / batching to avoid write pressure on the hot search path.

Ranking

Three signals applied in order of precedence:

  1. Operator boost — boost:desc always wins, regardless of category or popularity
  2. Category match — _eval(category:={category}):desc when a tab is active
  3. Popularity — popularity:desc as the final tiebreaker

When category is supplied:

sort_by = "boost:desc,_eval(category:={category}):desc,popularity:desc"

When category is absent:

sort_by = "boost:desc,popularity:desc"

Operator-boosted terms always appear first for every user on every tab. If the active category has no matching suggestions, global results fill the gap — no category ever returns an empty list. Suppressed terms (boost: -1) sink below all organic results without being deleted.

Boost and pinning

Operators can manually promote or suppress any suggestion by setting its boost value. All other fields (popularity, category, type) are managed automatically — only boost requires operator input. The nightly job never overwrites the boost field.

Boost values

ValueEffect
1Promoted — always appears above organic results
0Normal — ranked by category match and popularity (default)
-1Suppressed — sinks below all organic results; stays in collection for auditing

Use cases

Campaign promotion

Boost "samsung deals" and "black friday accessories" before a sale event. Remove the boost after the campaign ends — popularity takes over.

New product launch

Boost "iphone 17 pro" on launch day before organic search history has accumulated. Once popularity crosses a meaningful threshold the boost can be removed.

Suppress low-quality terms

Set boost: -1 on terms that appear in queries but generate zero clicks — e.g. misspellings that survived typo-tolerance, or overly generic single-word terms.

Each index detail view has a Suggestions tab alongside Overview, Connector, Documents, Search, and Api. Boost scope: changes made in the Suggestions tab apply globally — a suggestion promoted from the Accessories tab appears promoted on the PLP for all users, not just users browsing that index.

Suggestion Link Mode

Each suggestion has a mode field with two values. For support and account indexes, each trigger phrase maps to exactly one page — link mode sends the customer directly there without showing a results list. For catalog indexes, search mode is used, optionally with docs pinned to the top.

ModePLP behaviourUse case
searchFill search bar and run search (default)Catalog queries, broad terms
linkNavigate directly to the attached URLSupport pages, account pages, known single-answer intents

Pin to top — featured_doc_ids

featured_doc_ids is an ordered list of Typesense document IDs applied to search-mode suggestions. The first ID lands at position #1, the second at #2, and so on.

How pinning works in the backend:

  1. Client calls POST /v1/indexes/{id}/search/public; optional pinned_hits field carries client-supplied IDs.
  2. Backend calls get_featured_doc_ids_for_query(q) — an exact-match lookup in search_suggestions for the search query.
  3. If a matching suggestion has featured_doc_ids, those are used (client-supplied IDs take precedence when both are provided).
  4. For lexical search (search_documents): IDs passed as Typesense native pinned_hits in "id1:1,id2:2" format.
  5. For hybrid / semantic search (search_with_vec): native pinned_hits is unavailable (Python-side RRF is used). Missing pinned docs are fetched individually by ID and injected with an artificially high RRF score.
Client-agnostic auto-pin. Pinning is applied by the backend for any exact query match, from any client on any port — no PLP code change is required for new indexes.

extractSuggestions — link mode and pin seeding

function extractSuggestions(doc) {
  return [
    { query: "transfer my number", url: doc.url },       // link mode
    { query: "iphone 17 pro max",  doc_id: doc.id }      // search mode + pin at #1
  ];
}

When url is present, the seeder stores it in search_suggestions.url and sets mode = "link" automatically. When doc_id is present, it is stored in featured_doc_ids for auto-pin. Existing extensions that return { query } only are unaffected.

PLP typeahead behaviour

function selectSuggestion(s) {
  if (s.mode === 'link' && s.url) {
    window.location.href = s.url;           // direct navigation, no search
    return;
  }
  appStateStore.update(st => ({ ...st, query: s.text, page: 1 }));
  triggerSearch(s.featured_doc_ids?.length ? s.featured_doc_ids : undefined);
}

When the user presses Enter without selecting from the dropdown, _matchSuggestion(query) does an exact-match lookup against the loaded suggestions and applies featured_doc_ids for the typed query.

Future: LLM-assisted suggestion enrichment Phase 3

Motivation

The JS extension system extracts phrases that are explicitly present in document fields — manufacturer, OS, category slug, "for X" device targets. It cannot infer terms that are semantically implied but not literally present.

Document titleWhat JS extractsWhat an LLM would add
"Powerstation Mini 5K w/ Stand" "charger", "mophie charger" "power bank", "portable charger", "travel charger"
"Qi2 Mini Wireless Charging Car Vent Mount" "wireless charger", "car mount" "phone holder for car", "qi2 charger", "magnetic car mount"
"ZAGG XTR5 Screen Protector" "screen protector", "zagg screen protector" "tempered glass", "premium screen protector", "shatterproof glass"

Proposed design

Add an optional _run_llm_enrichment(docs, intent_label) step in suggestion_service.py that runs after JS extraction, before deduplication. Skipped entirely when no LLM API key is configured — opt-in, never breaks environments without external API access. 

JS extension
    ↓ phrase_pairs
LLM enrichment  ← opt-in, only if ANTHROPIC_API_KEY or OPENAI_API_KEY set
    ↓ additional phrase_pairs
Deduplicate → delete stale → upsert

Batching strategy

Calling the LLM once per document is slow and expensive. Batch 10–20 docs per call:

  • 542 accessories ÷ 15 per batch ≈ 37 API calls per rebuild
  • ~200 tokens in + ~150 tokens out per batch ≈ 13 K tokens total
  • Cost at Claude Haiku pricing: ~$0.02 per full accessories rebuild
  • Latency: ~30–60 seconds (parallelisable with asyncio.gather)

Prompt contract

You are a search suggestion generator for a telecom accessory catalog.
Given the following product documents, return a JSON array of search phrases
a customer might type to find these products. Phrases should be 2–5 words,
lowercase, generic enough to match multiple products.

Documents:
[{ "title": "...", "category": "...", "manufacturer": "..." }, ...]

Return only: ["phrase 1", "phrase 2", ...]
No explanation.
Implementation notes
Use the API key already stored in ISP settings — no new credential management needed.
Recommended model: Claude Haiku or GPT-4o-mini — fast and cheap, sufficient for structured phrase generation.
LLM-generated phrases get type="catalog" and participate in the same boost and refresh cycle.
The LLM step is additive — it supplements JS extraction, never replaces it. If the LLM call fails, the seeder continues with JS-only results.
Cap LLM suggestions per document at 5–8 to avoid flooding the collection with low-quality phrases.

Fast Autocompletion Search with a Succinct Index
Bast, H., & Weber, I. (2006). Type less, find more: Fast autocompletion search with a succinct index. Proceedings of SIGIR 2006, pp. 364–371. doi:10.1145/1148170.1148234
Establishes prefix-match over a ranked suggestion list as the correct retrieval model for typeahead — the same model used by Typesense's prefix search and the num_typos: 1 tolerance in the suggest endpoint.

Query suggestion from search logs

Query Recommendation Using Query Logs
Baeza-Yates, R., Hurtado, C., & Mendoza, M. (2004). Query recommendation using query logs in search engines. Proceedings of EDBT Workshops 2004, LNCS 3268, pp. 588–596. doi:10.1007/978-3-540-30192-9_58
Establishes that past search queries are the highest-quality source of suggestion candidates. Directly motivates Source 2 (nightly job over search_events) as the primary driver of the popularity field.
Mining Query Logs
Silvestri, F. (2010). Mining query logs: Turning search usage data into knowledge. Foundations and Trends in Information Retrieval, 4(1–2), 1–174. doi:10.1561/1500000013
Comprehensive treatment of query log analysis including frequency aggregation, session boundary detection, and temporal windowing. The 30-day rolling window and minimum query length (≥ 2 chars) are consistent with practices described here.

Prefix search and trie data structures

Trie Memory
Fredkin, E. (1960). Trie memory. Communications of the ACM, 3(9), 490–499. doi:10.1145/367390.367400
The original trie paper — the basis for all prefix-match autocomplete indexes, including Typesense's internal suggestion lookup. Prefix traversal in a trie is O(|prefix|) regardless of collection size.

Popularity and implicit feedback weighting

Collaborative Filtering for Implicit Feedback Datasets
Hu, Y., Koren, Y., & Volinsky, C. (2008). Collaborative filtering for implicit feedback datasets. Proceedings of ICDM 2008, pp. 263–272. doi:10.1109/ICDM.2008.22
Foundational paper for treating implicit signals as confidence-weighted preferences. The popularity field accumulates search frequency as an implicit confidence score — higher frequency = higher confidence that the term reflects real user intent.
Collaborative Filtering with Temporal Dynamics
Koren, Y. (2009). Collaborative filtering with temporal dynamics. Proceedings of KDD 2009, pp. 447–456. doi:10.1145/1557019.1557072
Demonstrates that recency matters in implicit signal aggregation. Motivates the 30-day rolling window rather than an unbounded all-time count, so that a viral term from 6 months ago does not permanently dominate suggestions.

Contextual and category-scoped suggestions

Faceted Search
Tunkelang, D. (2009). Faceted search. Synthesis Lectures on Information Concepts, Retrieval, and Services. Morgan & Claypool. doi:10.2200/S00190ED1V01Y200904ICR005
Covers faceted navigation — organising suggestions by category and structured dimensions. The category-scoped suggestion approach is an application of faceted relevance: the active facet selection improves suggestion precision.
Context-Sensitive Information Retrieval Using Implicit Feedback
Shen, X., Tan, B., & Zhai, C. (2005). Context-sensitive information retrieval using implicit feedback. Proceedings of SIGIR 2005, pp. 43–50. doi:10.1145/1076034.1076045
Shows that using session context (active category, previous queries) improves retrieval precision significantly. Directly motivates the category parameter and _eval(category:=X):desc boost expression.

Editorial boost and merchandising

Learning to Rank from Clickthrough Data
Joachims, T. (2002). Optimizing search engines using clickthrough data. Proceedings of KDD 2002, pp. 133–142. doi:10.1145/775047.775067
Establishes that click signals carry position bias. This is why suppressed terms (boost: -1) are kept in the collection rather than deleted — deleting them would allow re-entry via the nightly job and accumulation of biased clicks from earlier high-position exposure.
Controlled Experiments for Search Engine Result Page Merchandising
Chapelle, O., Joachims, T., Radlinski, F., & Yue, Y. (2012). Large-scale validation and analysis of interleaved search evaluation. ACM Transactions on Information Systems, 30(1), 6. doi:10.1145/2094072.2094078
Covers interleaved evaluation of editorial pinning vs organic ranking — directly relevant to validating that pinning a specific doc to position #1 actually improves task completion without harming the surrounding results. Motivates the choice to make featured_doc_ids operator-controlled rather than learned.
Rank Fusion for Result Diversification
Cormack, G. V., Clarke, C. L. A., & Buettcher, S. (2009). Reciprocal rank fusion outperforms Condorcet and individual rank learning methods. Proceedings of SIGIR 2009, pp. 758–759. doi:10.1145/1571941.1572114
The foundational RRF paper. ISP uses RRF to merge lexical and semantic candidate sets in search_with_vec. Because RRF works entirely on ranks (not raw scores), injecting a pinned doc with a very high artificial score is stable — it does not distort the relative ordering of unpinned results.

General information retrieval

Introduction to Information Retrieval
Manning, C. D., Raghavan, P., & Schütze, H. (2008). Introduction to information retrieval. Cambridge University Press. Freely available: nlp.stanford.edu/IR-book
Chapter 3 (Dictionaries and tolerant retrieval) covers prefix search, wildcard queries, and edit-distance tolerant matching — the theoretical basis for num_typos: 1 prefix search in the suggest endpoint.
