Architecture

Backend 5-layer design and frontend 7-layer data architecture.

Backend — 5-Layer Architecture

The backend is a FastAPI application. All code lives under backend/src/isp/. Layers communicate strictly downward — routers never touch the database directly.

LayerResponsibilityLocation
Config Load env vars / .env into a typed Settings object. Imported as module-level singleton settings. Never mutated at runtime. config.py
Models Pydantic request/response/config shapes. Split by domain, barrel re-exported from models/__init__.py. Always import as from isp.models import X. models/
Router HTTP endpoints, input validation, background task dispatch. Never calls PostgreSQL or Typesense directly. routers/<domain>.py
Domain Service PostgreSQL CRUD for one domain. Orchestrates infrastructure services. No FastAPI imports. services/domain/<domain>_service.py
Infrastructure Service Thin, pure-function wrappers around external systems (Typesense, Redis, V8, httpx). Never import from routers. services/infra/<name>.py
Key rule: Routers never call database.py or typesense_client.py directly. All I/O goes through a domain service. Infrastructure services are never called from routers.

Frontend — 7-Layer Architecture

The frontend is an Astro + Svelte SPA. All application code lives under frontend/src/. Data flows in one direction only — nothing lower in the stack may import from anything higher. 

Types → Repository → Mapper → Service → Store → Component → Helper

│  Component  │ ◄──────────────────────────────── │    Store     │

LayerResponsibilityLocation
Types DTO shapes and UI-state types. Split by domain, re-exported from a barrel index.ts. Always import as import type { X } from '../lib/types'. src/lib/types/
Repository Raw HTTP calls only. Returns unmodified DTOs. No mapping, no business logic, no store access. src/lib/repository/<Domain>Repository.ts
Mapper Pure functions. DTO → domain model. No async, no side effects. src/lib/services/<domain>/<domain>.mapper.ts
Service Calls repository + mapper. No direct HTTP. No this.set() on stores. Exported as singleton. src/lib/services/<domain>/<Domain>Service.ts
Store Svelte reactive state extending StoreBase<T>. Exposes action methods. Immutability rule: always this.update(s => ({ ...s, ... })). src/lib/stores/<domain>-store.ts
Component UI only. Reads store via $: x = $store.field. Calls store action methods. Never calls a repository or api.* directly. src/components/<domain>/
Helper Pure functions, no async, no store/service access. Co-located with the component that owns them. src/components/<domain>/<ComponentName>.helpers.ts

Anti-patterns (never do these)

Anti-patternWhy it is wrong
Component calls api.* or a repository directlyBypasses the store; state becomes inconsistent across components
Service calls this.set() on a storeService would depend on a higher layer; breaks unidirectional flow
Repository maps DTO → domain modelRepository must return raw DTOs so mappers stay pure and testable
Two components independently calling the same service endpointCreates duplicated network calls and divergent state; use a shared store
Mutating nested store state in placeSubscribers will not re-render without a new object reference
Mapper imported and called inside a componentMapping is orchestration — belongs in the service layer
