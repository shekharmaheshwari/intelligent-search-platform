Customer Context

A complete reference for how ISP uses customer behaviour to contextualise search results: what signals are collected, how they influence ranking, and every available personalisation option.

Why customer context

Two customers searching the same query want different things. Without context, both get the same ranked list. ISP adds context in two stages: first it scores every product for relevance (RRF), then it adds a personalisation layer on top (affinity). Neither stage hides results — they only shift the order.

Step 1 — Relevance score: BM25 + Semantic → RRF

Every search runs two passes simultaneously and fuses them with Reciprocal Rank Fusion (RRF):

  • BM25 — keyword engine: finds products whose titles and descriptions contain the exact search words.
  • Semantic — meaning engine: uses vector embeddings to find products that mean the same thing, even without exact word overlap ("warm coat" matches "winter jacket").
  • RRF — takes the ranked list from each engine and merges them into a single score using rank position, not raw scores.
── RRF formula ───────────────────────────────────────────────── RRF(d) = 1 / (k + rank_bm25) + 1 / (k + rank_semantic) k = 60 ── Worked example: search "wireless earbuds" ─────────────────── Sony WH-1000XM6 BM25 rank #1, semantic rank #1 RRF = 1/(60+1) + 1/(60+1) = 0.0164 + 0.0164 = 0.033 Samsung Galaxy Buds BM25 rank #8, semantic rank #10 RRF = 1/(60+8) + 1/(60+10) = 0.0147 + 0.0143 = 0.029 Sony ranks higher because it appeared near the top in BOTH engines. Samsung appeared later in both — lower RRF despite being a great product.

The RRF score is purely about relevance to the search query. No customer history is involved yet.

Step 2 — Personalisation layer: the affinity boost

After RRF produces a relevance ranking, ISP checks each product against the customer's session history and adds a small boost. The boost is proportional to how strongly the customer has shown interest in that product's category, brand, and type.

── Affinity formula ───────────────────────────────────────────── affinity(d) = 0.20 × category_affinity[d.category] + 0.15 × manufacturer_affinity[d.manufacturer] + 0.10 × type_affinity[d.type] ── Customer: viewed 3 Samsung phones ─────────────────────────── manufacturer_affinity["samsung"] = 1.00 ← viewed Samsung ×3 category_affinity["smartphones"] = 1.00 ← all were phones category_affinity["earbuds"] = 0.00 ← never viewed earbuds type_affinity["accessory"] = 0.00 ← all were devices ── Affinity per product in "wireless earbuds" results ────────── Samsung Galaxy Buds 3 (category: earbuds, brand: samsung, type: accessory) affinity = 0.20×0.00 + 0.15×1.00 + 0.10×0.00 = +0.15 ← brand match only Sony WH-1000XM6 (category: earbuds, brand: sony, type: accessory) affinity = 0.20×0.00 + 0.15×0.00 + 0.10×0.00 = +0.00 ← no match final score = RRF score + affinity boost

When category mismatch protects the customer — Alex's office chair

Alex has spent the last session buying gaming gear (Logitech keyboard, mouse, headset). Now Alex searches "ergonomic office chair". This is the hardest case: session history points one way, search intent points the other.

Bad personalisation (override): a naive system ignores the RRF score entirely and forces gaming items to the top.

The safety ceiling — editorial boost always beats maximum affinity

The maximum possible affinity boost is +0.45 (all three dimensions at 1.0). The is_featured editorial boost is +0.50. A featured product always outranks a maximally-boosted personalised one.

── Safety property ────────────────────────────────────────────── Sony WH-1000XM6 (is_featured = true) final = RRF(0.033) + editorial(0.500) = 0.533 Samsung Galaxy Buds 3 (manufacturer affinity = 1.0) final = RRF(0.029) + affinity(0.150) = 0.179 0.533 > 0.179 → Sony stays #1 regardless of personalisation Max affinity (+0.45) cannot beat a single is_featured editorial boost (+0.50). A strong objective match always outranks a maximally personalised weak match.
Fig 3 — Score ceiling: editorial boost vs affinity boost vs pure relevance

Key guarantee: personalisation raises the floor for preferred items. It does not lower the ceiling for objectively strong ones.

Action types

Every customer interaction is represented as a CustomerAction object.

interface CustomerAction {
  type:          'view' | 'cart' | 'purchase' | 'search' | 'category';
  item_id?:      string;   // Typesense doc id — used for preference vector seeding
  item_type?:    string;   // "device" | "accessory"
  category?:     string;   // product category (e.g. "smartphones")
  manufacturer?: string;   // brand (e.g. "Samsung")
  query?:        string;   // past search query (type="search" only)
  timestamp?:    number;   // Unix ms — used for time-decay weighting
  weight?:       number;   // caller-supplied multiplier (default 1.0)
}

Time-decay

Why decay matters

An action taken 3 seconds ago is a much stronger signal than one taken 45 minutes ago. Without decay, a product the customer briefly glanced at an hour ago carries the same weight as one they just put in their cart.

Implemented — Phase 2 (planned)

Each action's effective weight is:

effective_weight = type_weight × caller_weight × exp(−age_seconds / half_life_seconds)

Half-lives by type:

TypeHalf-lifeAt 30 minAt 2 hoursAt 1 day
purchaseno decay100%100%100%
cart30 min50%6%< 1%
view15 min25%1.5%< 1%
search8 min8%< 1%< 1%
category5 min3%< 1%< 1%

purchase events do not decay within a session. If timestamp is absent the action is treated as age zero (full weight) — backward compatible with clients that do not yet send timestamps.

── Worked examples: same type, different ages ─────────────────────────────── Cart event, 45 minutes ago: base_weight = 2.0 half_life = 1800s age = 2700s decay_factor = exp(−2700 / 1800) = exp(−1.5) = 0.223 effective_w = 2.0 × 0.223 = 0.447 ← less than a fresh view View event, 2 minutes ago: base_weight = 1.0 half_life = 900s age = 120s decay_factor = exp(−120 / 900) = exp(−0.133) = 0.875 effective_w = 1.0 × 0.875 = 0.875 ← beats the stale cart Takeaway: a 2-minute-old view (0.875) outweighs a 45-minute-old cart add (0.447). Recency can override action type when signals are sufficiently spread in time.

Storage tiers

Tier 1 — Current session (sessionStorage)

  • Raw event list, newest first
  • Client-side cap: 20 events (controlled by MAX_SESSION_ACTIONS in the PLP)
  • Server-side cap: 50 actions processed per request (max_actions=50 in build_context())
  • Cleared when the browser tab/session closes
  • Minute-scale decay applied server-side via timestamp
  • Highest influence on results

Tier 2 — Visitor profile (localStorage) — planned

Persists across browser closes on the same device. Stores a compressed profile rather than raw events to avoid unbounded growth.

interface VisitorProfile {
  visitor_id:           string;           // UUID, generated once, no PII
  last_updated:         number;           // Unix ms
  category_weights:     Record<string, number>;
  manufacturer_weights: Record<string, number>;
  type_weights:         Record<string, number>;
  recent_item_ids: {
    id:           string;
    type?:        string;
    category?:    string;
    manufacturer?: string;
    ts:           number;
  }[];                                    // last 10, newest first
}

Profile TTL: 30 days. Items older than 30 days are pruned from recent_item_ids on each write.

Merge strategy on every search request: getHistory() produces a unified action_history array by taking all raw events from sessionStorage (real timestamps) and converting the localStorage profile into synthetic CustomerAction events with weight: 0.5. The server-side decay function handles both uniformly.

Tier 3 — Server-side profile (identified users) — planned

For customers who sign in via OAuth2. Profile stored in Redis (key: isp:visitor:{email}, TTL 30 days).

EndpointPurpose
GET /v1/visitor/profileReturns the server profile for the current JWT user
POST /v1/visitor/profileMerges a client VisitorProfile into the server profile

Tier merge — worked example

When the PLP makes a search call, getHistory() assembles the final action_history array by merging both tiers before sending to the server:

── Tier 1 (sessionStorage) — raw events, real timestamps ──────────────────── { type:"view", item_id:"buds-001", manufacturer:"Samsung", ts: now − 5 min } w = 1.0 { type:"search", query:"wireless earbuds", ts: now − 8 min } w = 0.5 ── Tier 2 (localStorage) — synthetic events, weight multiplied by 0.5 ────── { type:"view", item_id:"s25-001", manufacturer:"Samsung", ts: 3 days ago } w = 0.5 { type:"purchase",item_id:"case-001", manufacturer:"Samsung", ts: 7 days ago } w = 1.5 ── Merged array sent to server ─────────────────────────────────────────────── [ tier1_raw_events ] ++ [ tier2_synthetic_events × 0.5 weight ] ↑ full weight ↑ half weight — cross-session memory, less certain ↑ real ts ↑ ts from profile.last_updated Server applies time-decay uniformly across both tiers via the timestamp field. Result: recent tier1 events dominate; tier2 provides longitudinal brand context.

Preference vector blending

The primary personalisation mechanism for semantic and hybrid search. By blending viewed-item vectors into the query vector before the ANN call, retrieval naturally surfaces items that are both semantically relevant to the query and similar to what the customer has been looking at.

The algorithm

Step 1 — Collect item vectors. For each item_id in ctx.vector_seed_ids (up to 5, ordered by recency), fetch the stored vec embedding from Typesense.

Step 2 — Compute centroid (equal-weight mean). Average the item vectors dimension by dimension:

preference_vec[i] = (vec_1[i] + vec_2[i] + ... + vec_n[i]) / n
  Samsung Galaxy Buds  →  v₁  =  [ 0.82,  0.14,  0.55,  0.91, ... ]
  Samsung Phone Case   →  v₂  =  [ 0.79,  0.21,  0.48,  0.88, ... ]
  Samsung Charger      →  v₃  =  [ 0.85,  0.09,  0.61,  0.94, ... ]
                         p  =      [ 0.82,  0.15,  0.55,  0.91, ... ]   ← centroid

Mathematical basis: centroid computation is the direct descendant of the Rocchio (1971) relevance feedback algorithm. The vector space model was introduced by Salton, Wong & Yang (1975).

Step 3 — Linear blend with query vector.

blended[i] = 0.8 × query_vec[i]  +  0.2 × preference_vec[i]
  q  = embed("wireless earbuds")  →  [ 0.60,  0.88,  0.33,  0.72, ... ]
  p  = Samsung centroid           →  [ 0.82,  0.15,  0.55,  0.91, ... ]
  blended                         →  [ 0.64,  0.73,  0.37,  0.76, ... ]

This is the Rocchio update rule applied to dense vectors: Q_new = 0.8·Q_orig + 0.2·centroid(relevant). The 0.2 value prevents query drift — values above 0.5 cause semantically off-topic but "preferred-brand" items to flood results (Efthimiadis, 1996).

Step 4 — L2 normalisation (required for cosine-distance ANN search).

final_vec[i] = blended[i] / sqrt(Σ blended[i]²)

L2 normalisation — worked example

── Blended vector (first 4 of 1024 dims, NOT yet normalised) ──────────────── blended = 0.8 × q + 0.2 × p = 0.8 × [0.60, 0.88, 0.33, 0.72, ...] + 0.2 × [0.82, 0.15, 0.55, 0.91, ...] = [0.644, 0.734, 0.374, 0.758, ...] ── L2 norm (magnitude) ────────────────────────────────────────────────────── ‖blended‖ = sqrt(0.644² + 0.734² + 0.374² + 0.758² + ...) ≈ sqrt(0.415 + 0.539 + 0.140 + 0.575 + ...) ≈ 1.324 ── Divide every dimension by the norm ─────────────────────────────────────── final[0] = 0.644 / 1.324 = 0.486 final[1] = 0.734 / 1.324 = 0.554 final[2] = 0.374 / 1.324 = 0.282 final[3] = 0.758 / 1.324 = 0.572 ... (1024 dimensions total) verify: sqrt(0.486² + 0.554² + 0.282² + 0.572² + ...) ≈ 1.000 ✓
Fig 7 — 2D projection: query vector nudged toward Samsung item cluster

Why L2 normalisation?

Typesense's ANN index uses cosine similarity: cosine_sim(A, B) = (A · B) / (‖A‖ × ‖B‖). When both vectors are unit-length this simplifies to a plain dot product. After blending the norm is not 1, so normalisation is required.

Affinity boosts (post-RRF)

Applied after RRF merge and editorial boosts, before final page slice. These are additive score adjustments that nudge results toward the customer's demonstrated interests.

SignalBoostApplied when
Category match+0.20 × affinitymetadata.category matches a category in category_affinity
Manufacturer match+0.15 × affinitymetadata.manufacturer matches manufacturer_affinity
Source type match+0.10 × affinitysource_type matches type_affinity
Already viewed−0.05Doc id is in viewed_ids

All affinity values are normalised to [0,1] so maximum total boost is +0.45. Editorial boosts (is_featured +0.5, popularity ≤ +0.5) are larger — a featured item stays featured even for a customer with no category affinity.

How affinity is calculated

Step 1 — Accumulate weighted counts. For every action in action_history, compute w = type_weight × caller_weight and add to running sums keyed by category, manufacturer, and item_type.

Step 2 — Max-normalise to [0, 1].

affinity[k] = raw[k] / max(raw.values())

Step 3 — Apply as additive score boost per document.

boost = 0.20 × category_affinity.get(doc_cat,  0)
      + 0.15 × manufacturer_affinity.get(doc_mfr, 0)
      + 0.10 × type_affinity.get(doc_type, 0)
      − 0.05  (if doc.id is in viewed_ids)

Operator controls

ISP exposes four independent feature flags in Settings → Personalisation tab. All flags are cached in memory — there is no database round-trip per search request.

FlagDefaultEffect when off
Personalisation (master)Onaction_history is completely ignored; no context is built. All sub-flags become inert.
Preference Vector BlendingOnViewed-item vectors are not blended into the query. ANN uses raw query vector only.
Affinity Score BoostsOnCategory (+0.20), manufacturer (+0.15), and product-type (+0.10) adjustments are skipped.
Viewed Item PenaltyOnAlready-viewed items are not demoted (−0.05). Variety suppression is disabled.

The master toggle is a hard gate. A/B testing use: because each flag can be turned off independently, you can isolate the contribution of each personalisation signal.

Flags are stored in the app_settings PostgreSQL table and updated in place on every PUT /settings/customer-context call — no DB read on the hot search path.

Flag precedence

── master flag = OFF ───────────────────────────────────────────────────────── personalisation = false → action_history discarded on arrival → context_service.build_context() → empty context { } → preference_vector_blend = N/A (no context to blend) → affinity_boosts = N/A → viewed_item_penalty = N/A ── master = ON, sub-flags evaluated independently ──────────────────────────── preference_vector_blend ON → ANN query = 0.8×query_vec + 0.2×preference_vec (blended) OFF → ANN query = query_vec (raw, no personalisation in retrieval) affinity_boosts ON → doc.score += 0.20×cat + 0.15×mfr + 0.10×type OFF → doc.score unchanged (re-ranking is skipped entirely) viewed_item_penalty ON → doc.score −= 0.05 if doc.id ∈ viewed_ids OFF → all items treated equally regardless of prior views

Browse personalisation (empty-query)

When the search query is empty, the PLP frontend forces mode: 'lexical'. Because there is no query vector, preference vector blending cannot run. However, affinity boosts and the viewed-item penalty operate purely on document metadata and apply to browse.

Large-batch fetch: re-sorting only the first page would miss Samsung items at position 25+. When an affinity hook is active, _run_search paginates up to _MAX_BROWSE_PAGES = 4 pages (1 000 items), applies the hook over all results, then slices to the requested page.

Multi-page fetch — worked example

Without multi-page fetch, affinity can only affect items on page 1. Samsung Galaxy Buds 3 at position 25 would never surface. With the 4-page batch, it can:

── Samsung customer, empty query, page 1 (24 items) ───────────────────────── Without personalisation: Typesense returns items sorted by popularity + is_featured Samsung Galaxy Buds 3 → position 25 (just off page 1, never seen) With personalisation (_MAX_BROWSE_PAGES = 4, fetches 1 000 items): Each item gets a rank_score = 1 / (60 + position) (same RRF formula) Item #18 (no affinity): score = 1/(60+18) + 0.000 = 0.0128 Samsung Galaxy Buds 3, position 25, manufacturer_affinity = 0.87: rank_score = 1/(60+25) = 0.0118 affinity = 0.15 × 0.87 = 0.130 (manufacturer match only) final = 0.0118 + 0.130 = 0.142 >> item #18 (0.0128) ISP re-sorts all 1 000 items by final score, then slices [0:24] for page 1. Samsung Galaxy Buds 3 lands in page 1 position ~2 — affinity overcomes the rank gap.

Other personalisation options

Collaborative filtering

Offline nightly job reads search_events, computes co-view pairs, stores in co_view_pairs table (item_id_a, item_id_b, score). At search time, co-view partners of viewed items are used as additional preference vector seeds — personalises results for customers with zero current-session history.

Comprehensive survey of query expansion techniques. Directly cited in the preference vector section: blend weights above 0.5 cause query drift — the customer's preferred brand items flood results at the expense of the actual search intent. ISP uses 0.2 to prevent this.
