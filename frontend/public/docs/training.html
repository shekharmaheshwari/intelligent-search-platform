Trained Popularity Re-Scorer Case A — Done

A LogisticRegression model trained on real browse behavior replaces one piece of aggregate_popularity()'s hand-written CTR formula — decoupled from the existing analytics pipeline, its own module, its own router, its own table.

What it is

ISP's editorial popularity field was previously produced by a fixed formula: 1/log2(rank+2) decay summed per impression, hand-tuned rather than learned. This feature trains a real model on logged browse behavior instead — same field, same write path (update_document_fields), same downstream consumer (RRF post-scoring) — but the number written now comes from a calibrated model's predicted click probability, not a summed heuristic.

It is deliberately decoupled: analytics_service.py and routers/analytics.py have a zero diff. This is its own module (popularity_trainer.py), its own router (routers/training.py), its own table (training_runs) — deletable without touching the existing formula-based path.

Endpoint

POST /v1/training/popularity?index_id=<slug-or-id>&days=30

On-demand only, same operational model as /v1/analytics/aggregate — no scheduler is built. Triggering it repeatedly (cron, k8s CronJob, manual) is an operational decision outside this codebase.

Response fieldMeaning
docs_scoredDocuments that received a written-back popularity value this run
n_eventsRaw search_events rows matched by the query window (not the post-join usable-example count — see Review fixes)
aucHeld-out AUC from the grouped eval split, or null if skipped/degenerate

Pipeline

  1. Resolve the index (slug or hex id, same _resolve_index helper every other admin endpoint uses) and pull its stored affinity_dimensions config — the same dimensions affinity_service.discover() already computes. No rediscovery, no hardcoded field list.
  2. Pull training data: query search_events for this index, filtered to query = '' (browse-only impressions/clicks) within the lookback window. Fewer than 5 raw rows → log an empty training_runs row, return docs_scored: 0.
  3. Fetch every document's current fields via ts.list_documents() — the same call backing GET /v1/indexes/{id}/documents — paginated across the whole index.
  4. Build one feature dict per document — see Feature building.
  5. Join events to features, weighted by position: each event becomes one training example — clicked (0/1) as the label, the document's feature dict as X, and 1/log2(rank+2) as the training sample_weight. Events referencing a doc no longer in Typesense are dropped here.
  6. Vectorize and train: DictVectorizer turns mixed categorical/numeric feature dicts into a sparse matrix. A held-out 20% split (grouped by doc_id) gives a rough AUC when there's enough data (≥10 events); the real model is fit on everything.
  7. Score every document — not just ones with events, the model generalizes from features — and calibrate: popularity = round(raw / max_raw × 1,000,000), identical final normalization to the old formula.
  8. Write back via ts.update_document_fields() — the exact call apply_popularity already uses. No model inference in the search hot path; query time reads a flat field.
  9. Log the run to training_runs — index, model type, event/doc counts, held-out metric — so training history is queryable, not just the latest overwrite.

Feature building

_doc_features(doc, affinity_dims) builds a flat dict per document, with missing fields simply omitted — no per-vertical branching:

  • Every enabled affinity dimension's categorical value (one-hot-able)
  • For a derived dimension like price_tier — the raw underlying numeric value (e.g. price), not the bucket. Strictly more information for the model, and avoids duplicating context_service.py's threshold logic here
  • is_featured as a 1.0/absent flag
  • A rating signal when present: averageStarRating × log(1+ratingsCount)
  • A bounded recency feature from indexed_at: 1 / (1 + days_since_indexed)

Model & calibration

LogisticRegression, trained per index (not pooled), sample_weight-ed by the same 1/log2(rank+2) position-decay curve aggregate_popularity already used — as a training weight now, not a hand-summed score.

popularity = round(raw_predicted_probability / max_raw × 1_000_000)

Identical 0–1,000,000 output range to the formula it replaces, so nothing downstream (RRF post-scoring, the "Sort by Popularity" UI) needed to change.

⚠ Honest framing: the 1/log2(rank+2) weighting is a position-weighted heuristic, not propensity-corrected debiasing. Proper IPS/propensity correction is a documented, unbuilt v2 follow-up — see Deliberate v1 scope and researchTopic1ImplicitFeedbackRanking.md. Don't describe this as "position-debiased at production scale" — that overstates what's implemented, a mistake already caught and corrected once in the research-paper track for this feature.

Review fixes 3 findings, all fixed

A code review before this shipped found three real gaps between the "graceful empty" intent and what the code actually did. All three are fixed and covered by dedicated regression tests.

1. Zero-feature-matrix crash

An index with no discovered affinity dimensions and documents missing is_featured/rating/indexed_at produced an all-empty feature dict for every document. DictVectorizer then emits a zero-column matrix, and LogisticRegression.fit() raised ValueError: Found array with 0 feature(s) — reproduced directly before the fix. Now detected via X.shape[1] == 0, treated as the same graceful empty-run case as steps 2 and 5 of the pipeline.

2. Post-join threshold recheck

The 5-event minimum was checked against the raw query row count, before the event→document join dropped rows referencing deleted/missing docs. Five raw events could collapse to two usable examples post-join and still train — now re-checked as len(y) < _MIN_EVENTS immediately after the join, before vectorization.

3. Doc-grouped held-out AUC split

The original held-out split was per-event and stratifyd only on the label. Multiple events for the same document share an identical feature vector, so a random per-event split could leak the same document's features into both train and test, inflating the reported AUC. Switched to GroupShuffleSplit grouped by doc_id — verified this actually changes behavior, not just cosmetics: a 2-document, all-one-label-per-doc scenario now correctly produces auc: None (caught ValueError, single class landed on one side of the split) instead of the artificially-clean AUC the old stratified per-event split would have produced.

Deliberate v1 scope decisions

DecisionWhy
Trained per index, not pooledKeeps consistency with the existing per-index ?index_id= endpoint shape. Revisit if a specific index's traffic proves too sparse.
Position-weighting, not IPS/propensity correctionSame decay curve aggregate_popularity already used, applied as a training weight. Proper debiasing is a documented, unbuilt v2 follow-up.
Browse-only training data (query = '')Deliberate difference from the old formula, which pooled all traffic regardless of query.
Simple held-out AUC, not full counterfactual evalEnough to sanity-check the pipeline; not enough to claim relevance quality without real production traffic.
Raw numeric value for derived dimensionsModel sees actual price, not price_tier's bucket label — strictly more information, avoids duplicating threshold logic.

Verification

  • 6 router-level tests (tests/routers/test_training.py) — auth guard, unknown index, too-few-events, missing-Typesense-collection resilience, training_runs logging.
  • 7 domain-level tests (tests/domain/test_popularity_trainer.py), added specifically to close a coverage gap the router tests couldn't reach: they call train_and_apply() directly with Typesense mocked, driving the full path — vectorization, fit, calibration, write-back — and regression-guard each of the three review fixes above, including the grouped-split behavior change proven with a case that only fails under grouping.
  • 13 tests total, all passing alongside the rest of the backend suite.
  • Live end-to-end run against the Phones index (22ffabfef4d1): seeded real search_events, called the endpoint, confirmed a trained model (AUC 0.75 on an 11-event seed set) wrote calibrated popularity values in range, logged a training_runs row. Seed data and resulting scores were removed/restored afterward — a mechanical pipeline check, not a relevance-quality claim.

What this doesn't do yet

  • Case B (query-conditional boost) and Case C (personalized affinity weights) Design only — see trainedRescorerDesign.md.
  • No scheduler — on-demand only, same as /v1/analytics/aggregate.
  • No IPS/propensity correction — position-weighted, not position-debiased in the rigorous sense. Documented v2 follow-up.

References

Implicit feedback and click-through data

Optimizing Search Engines Using Clickthrough Data
Joachims, T. (2002). KDD 2002. doi.org/10.1145/775047.775067
Foundational justification for treating clicks as implicit relevance labels — the basis for using clicked as the training target here.
An Experimental Comparison of Click Position-Bias Models
Craswell, N., Zoeter, O., Taylor, M., & Ramsey, B. (2008). WSDM 2008. doi.org/10.1145/1341531.1341545
Formalizes position bias in click data — the reason a raw CTR formula (and this model's 1/log2(rank+2) sample weight) needs the honest "position-weighted, not debiased" caveat above.
Unbiased Learning-to-Rank with Biased Feedback
Joachims, T., Swaminathan, A., & Schnabel, T. (2017). WSDM 2017. dl.acm.org
Defines inverse-propensity-scored (IPS) correction — the specific technique the "Deliberate v1 scope" section names as the unbuilt v2 follow-up.

Model and tooling

Applied Logistic Regression (3rd ed.)
Hosmer, D. W., Lemeshow, S., & Sturdivant, R. X. (2013). Wiley. ISBN: 978-0470582473.
Standard reference for the model class used here — chosen for interpretability and stability on the sparse-per-item interaction volume a single index typically has.
Scikit-learn: Machine Learning in Python
Pedregosa, F. et al. (2011). Journal of Machine Learning Research, 12. jmlr.org
DictVectorizer and LogisticRegression — chosen specifically because mixed categorical/numeric feature dicts are exactly what DictVectorizer is for, with no pandas dependency needed.

Evaluation methodology

Cross-Validation Strategies for Data with Temporal, Spatial, Hierarchical, or Phylogenetic Structure
Roberts, D. R. et al. (2017). Ecography, 40(8). doi.org/10.1111/ecog.02881
General treatment of the exact leakage problem the doc-grouped held-out split fixes: non-independent samples (here, multiple events per document sharing one feature vector) inflate held-out performance under a naive random split.
An Introduction to ROC Analysis
Fawcett, T. (2006). Pattern Recognition Letters, 27(8). doi.org/10.1016/j.patrec.2005.10.010
Standard reference for the AUC metric reported as this pipeline's held-out sanity check.
