Boost Rules

Rule-based inventory boosting — operator-defined merchandising score adjustments applied post-RRF, with browse and search modes, trigger+targets logic, and a doc-picker for exact-ID targeting.

What it is

Boost Rules let operators apply additive score boosts to product subsets using two-part conditional logic:

  • Trigger — when the rule fires (all conditions AND-ed)
  • Boost targets — which products are boosted (any condition OR-ed)

Rather than boosting a single named document (which Suggestions / Pin-to-top handles), Boost Rules target a class of products — every Apple device when someone searches "iphone", every item whose title contains "clearance" on the browse page, or a specific product ID when a particular search term is used.

Data model

Criterion

A single field-match condition used in both trigger and targets:

{ "field": "manufacturer", "operator": "equals", "value": "apple" }
FieldTypeValues
fieldstringAny filterable schema field, "id", or "__search_term__" (trigger only)
operatorenum"equals" / "contains" / "regex"
valuestringThe match target

The special field __search_term__ matches against the live search query string rather than any document field. It is only meaningful in the trigger section.

Rule block

{
  "id":      "rule_abc123",
  "label":   "Apple search boost",
  "enabled": true,
  "boost":   0.40,
  "trigger": [
    { "field": "__search_term__", "operator": "contains", "value": "apple" }
  ],
  "targets": [
    { "field": "id",           "operator": "equals",   "value": "PROD-001" },
    { "field": "manufacturer", "operator": "equals",   "value": "apple"    },
    { "field": "title",        "operator": "contains", "value": "iPhone"   }
  ]
}
FieldTypeNotes
idstringGenerated on creation (nanoid)
labelstringHuman-readable name shown in the rule card header
enabledboolToggle without deleting — takes effect immediately
boostfloatAdditive score delta. Range 0.00–1.00, clamped server-side.
triggerlistALL must match (AND). Supports __search_term__. Empty = matches nothing.
targetslistANY must match (OR). Empty = all documents passing the trigger are boosted.

Index-level storage

Rules are stored in a boost_rules JSONB column on the indexes table — one list of rule blocks per index. Migration:

ALTER TABLE indexes ADD COLUMN IF NOT EXISTS boost_rules JSONB DEFAULT '[]';

Legacy migration: rules saved before the trigger+targets redesign (with a flat criteria key) are automatically upgraded on load — criteria becomes trigger, targets defaults to [].

Browse vs search gate

The gate is evaluated per-rule, not globally. Whether a rule fires depends on the presence of __search_term__ in its trigger:

Trigger contains __search_term__?Fires when
YesActive query is non-empty AND the query matches the trigger
NoBrowse only (empty query)

Different rules in the same index can mix modes — some search-mode, some browse-mode — evaluated independently.

Boost value zones

Normal zone — 0.00 to +0.45

Track colour: accent (blue/purple). Products move up in rankings but strong relevance matches still appear above weak ones.

"Applies a preference nudge. Natural search relevance remains intact."

Danger zone — +0.50 to +1.00

⚠ Warning: Boosts ≥ +0.50 aggressively override keyword and semantic relevance. Products matching this rule may jump to the top even for loosely related queries. Hard cap: +1.00 in both UI and backend.

Score context

At K=60 RRF, a boost of +0.50 matches or exceeds the full base score of a mid-ranked document — the quantitative basis for the danger zone boundary.

RRF rankApproximate base score
Position 1~0.061
Position 5~0.055
Position 20~0.043

A boost of +0.30 roughly matches the "featured" editorial boost — moves a product well up the page without guaranteeing position 1. A boost of +0.70 overrides almost any relevance signal.

Trigger / Targets logic

Trigger — ALL must match (AND)

Trigger:
  __search_term__  contains  "apple"

→ fires only when the search query contains "apple"

Mixed triggers (search term + field) are supported but uncommon:

Trigger:
  __search_term__  equals    "iphone"
  manufacturer     equals    "apple"

→ fires only when searching "iphone" AND the document is made by Apple

Targets — ANY must match (OR)

Once the trigger fires, a document is boosted if it matches any target row. Empty targets = boost all documents that passed the trigger.

Targets (OR):
  id           equals    "PROD-001"
  manufacturer equals    "apple"
  title        contains  "iPhone"

→ boosts PROD-001, or any Apple product, or any product with "iPhone" in the title

OR across rules

Create separate rule blocks. Each is evaluated independently and applies its own boost. A document matching two blocks receives both boosts (stacking additively).

ID target & Browse picker

When id is selected as the target field, the plain text input is replaced by a document Browse picker — the same DocPickerModal used for Pin-to-top in Suggestions:

┌─ Boost targets (OR) ───────────────────────────────────────────────┐
│  id ▼   Equals ▼   [ iPhone 15 Pro          PROD-001    ✕ ]  Browse│
│  [+ Add target condition]                                           │
└─────────────────────────────────────────────────────────────────────┘

Clicking Browse opens a search-and-select modal. The picked document's title is shown in the chip for readability; only the ID is saved in the criterion value. This makes it easy to pin an exact product for a specific search term without copy-pasting doc IDs.

Field list — filtered live schema

Target dropdown fields come from the live Typesense collection schema filtered through a server-side blocklist:

Always excluded (system internals):
vec, indexed_at, metadata, content, url, is_featured, popularity, version_score, in_stock, price, boost_queries_equal, boost_queries_contains, images, skus, color_options, aliases, tags

id is excluded from the API field list but hardcoded as the first option in the targets dropdown (with Browse picker behaviour). __search_term__ is hardcoded as the first option in the trigger dropdown only.

Backend application

_SEARCH_TERM_FIELD = "__search_term__"

def apply_boost_rules(scores, all_docs, rules, query=""):
    is_search = bool(query.strip())
    for rule in rules:
        if not rule.get("enabled", True): continue
        boost   = min(float(rule.get("boost", 0.0)), 1.0)
        trigger = rule.get("trigger", [])
        targets = rule.get("targets", [])
        if not trigger or boost == 0.0: continue

        # Per-rule browse/search gate
        has_query_criterion = any(
            c["field"] == _SEARCH_TERM_FIELD for c in trigger
        )
        if has_query_criterion != is_search:
            continue

        for did, doc in all_docs.items():
            meta = _parse_meta(doc)
            # Trigger: ALL must match (AND)
            if not all(_check_criterion(c, doc, meta, query) for c in trigger):
                continue
            # Targets: ANY must match (OR); empty = boost all
            if targets and not any(
                _check_criterion(c, doc, meta, query) for c in targets
            ):
                continue
            scores[did] = scores.get(did, 0.0) + boost

Where it runs

  • search.py — single-index hybrid/semantic/lexical search: wired into post_rrf_hook after personalisation
  • catalog.py — cross-index catalog search: rules merged from all non-external indexes, same hook position
  • Browse-only rules are skipped during search; search-only rules are skipped during browse — determined per-rule inside apply_boost_rules

References

Boolean retrieval and AND logic

Introduction to Information Retrieval
Manning, C. D., Raghavan, P., & Schütze, H. (2008). Cambridge University Press. nlp.stanford.edu/IR-book
Chapter 1 defines the Boolean retrieval model — the theoretical foundation for AND-chained trigger evaluation. _check_criterion with all-AND across trigger is a direct conjunctive Boolean query over document field values.

Field-specific boosting (BM25F)

BM25F — Simple BM25 Extension to Multiple Weighted Fields
Robertson, S., Zaragoza, H., & Taylor, M. (2004). CIKM 2004. dl.acm.org
Motivates field-selective boosting: different fields carry different discriminating power. Targeting title (contains "clearance") vs manufacturer (equals "apple") applies the same principle BM25F formalises.
The Probabilistic Relevance Framework: BM25 and Beyond
Robertson, S., & Zaragoza, H. (2009). Foundations and Trends in Information Retrieval, 3(4). doi.org/10.1561/1500000019
Establishes that additive per-field score contributions are both theoretically grounded and empirically effective — the same principle that makes additive boost rules predictable and composable.

Score combination and stacking

Analyses of Multiple Evidence Combination
Lee, J. H. (1997). SIGIR 1997. dl.acm.org
Demonstrates that linear additive combination of independent evidence signals is robust — the theoretical basis for stacking boost rules additively. Also motivates the hard cap at +1.00.
Reciprocal Rank Fusion
Cormack, G. V., Clarke, C. L. A., & Buettcher, S. (2009). SIGIR 2009. dl.acm.org
Defines RRF and the score range context for calibrating the danger zone. At K=60, a +0.50 boost matches or exceeds the full base RRF score of a mid-ranked document — the quantitative basis for the +0.50 boundary.

E-commerce search and merchandising

On Application of Learning to Rank for E-Commerce Search
Karmaker Santu et al. (2017). SIGIR 2017. dl.acm.org
Identifies the tension between pure relevance and business objectives. Finds that purely relevance-based ranking systematically under-serves business goals — directly motivating Boost Rules as a first-class merchandising tool.

Rule matching and pattern evaluation

RETE: A Fast Algorithm for the Many Pattern / Many Object Pattern Match Problem
Forgy, C. L. (1982). Artificial Intelligence, 19(1). doi.org
The foundational rule-matching algorithm. ISP's linear scan is appropriate for <50 rules and <1 000 candidate documents. If rule or candidate counts grow, RETE-style partial match caching becomes the right optimisation.
Regular Expression Matching Can Be Simple and Fast
Cox, R. (2007). swtch.com
Python's re module can exhibit O(2ⁿ) worst-case on adversarial patterns. Patterns are validated at save time; consider complexity limits to prevent ReDoS if patterns are operator-supplied.

Relevance vs business objectives

Learning to Rank for Information Retrieval
Liu, T. Y. (2009). Foundations and Trends in Information Retrieval, 3(3). doi.org
Hard business constraints are best handled as post-processing overrides rather than training signals — exactly the architecture ISP uses: relevance ranking first, then boost-rule overrides.
Unbiased Learning to Rank with Biased Feedback
Joachims, T., Swaminathan, A., & Schnabel, T. (2017). WSDM 2017. dl.acm.org
When a boost rule forces a product to position 1, CTR signals for that position become contaminated — clicks reflect position, not preference. The hidden cost of aggressive boosting that the danger-zone warning implicitly communicates.

Merchandising and retailing

Retailing Management (9th ed.)
Levy, M., Weitz, B., & Grewal, D. (2019). McGraw-Hill Education. ISBN: 978-1260260786.
Digital search boost rules are the online equivalent of physical end-caps: placing promoted products at the top of the result set performs the same function as a physical promotional display.
The Long Tail: Why the Future of Business Is Selling Less of More
Anderson, C. (2006). Hyperion. ISBN: 978-1401302375.
Boost rules targeting specific manufacturers or categories during campaigns are a direct tool for shifting the revenue distribution temporarily — pushing clearance items or new launches into the head of the distribution for the campaign window.
