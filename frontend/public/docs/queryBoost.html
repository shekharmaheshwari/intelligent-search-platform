Learned Query Boost Case B — Done

Learns from clicks which products shoppers actually pick for each kind of query, and gives those products a small, bounded lift the next time someone searches something similar. It can retrain daily per index.

What it is

Before this, ranking for a typed query came from text and vector relevance (RRF), hand-set levers (is_featured, pins, boost_queries_*, boost rules) and a query-agnostic popularity score (Case A). Nothing learned "for this query, people pick that product". The learned query boost fills that gap:

  1. Groups similar queries ("cheap iphone", "budget iphone") by embedding similarity, so each query doesn't need its own large sample.
  2. Finds products that over-perform within a group: click rate against the group's average, with lower-ranked results counted less, and sparse evidence shrunk toward the average.
  3. Adds a small lift to those products for queries in the same group, including new wordings matched by meaning in hybrid or semantic mode.

This is counting plus empirical-Bayes shrinkage, not a regression or learning-to-rank model. Every boost traces back to raw impression and click counts.

It's decoupled: its own package, services/domain/query_boost/, its own tables and its own routes. Its only touch points are a few lines in the search and catalog routers and the scheduler's start and stop in main.py.

Possible result flags from a training run:

  • trained: a new model was published.
  • superseded: the model was deleted or replaced, or the schedule turned off, during the run, so the result was discarded.
  • trained:false with neither: too little traffic (fewer than 5 usable events), and the previous model is kept.

How it learns

  1. Read events: query (non-browse) search_events for the index within the last days. Impression rows and click rows are counted separately. A click is not also an impression.
  2. Filter: drop browse ("", *) and superlative queries ("cheapest phone"), and keep the 500 most frequent distinct queries.
  3. Embed and group: using the index's own embedding model (the same one search uses). Greedy leader clustering at cosine ≥ 0.85.
  4. Score: each event is weighted by 1/log2(rank+2). Each document's click rate is shrunk toward its group's baseline p_c (prior strength 5), then boost = max(0, shrunk − p_c) / (1 − p_c), which falls in [0, 1].
  5. Publish: replace the index's model in one transaction, keeping every group, including ones with no boosted documents, as matching boundaries. Log a training_runs row (case B, ctr_shrinkage).

Serving & safety

  • Matching: a query seen in training uses its own group, with no embedding call. A new query is matched by vector only in hybrid or semantic mode, where the query is embedded anyway, and only if the index's embedding model is the one the model was trained with.
  • Magnitude: score += boost × 0.008. That's about half the #1 RRF score, enough to lift a clearly preferred result up the page. It stays far below the manual levers (is_featured +0.5, boost_queries_* +0.3/+0.5) and pins, so manual merchandising always wins.
  • Exact-title guard: if any candidate's title or alias exactly equals the query, the learned boost is skipped for that search.
  • Browse is untouched: empty-query listings are Case A's job.
  • Catalog (PLP) search: boosts are resolved per source index and keyed index:doc. Searches that use it report learned_query_boost in context_actions_used.

Batch learning schedule

Each index can retrain itself once a day. It's off by default.

SettingDefaultMeaning
enabledfalseDaily retraining on or off
days30Lookback window per run (1–365)
run_hour_utc2Hour of day, in UTC, the run starts (0–23)
  • The scheduler checks every 60 s. A run is due when the latest run_hour_utc:00 UTC is after the time the schedule was enabled and hasn't run yet.
  • Turning it on, or changing the hour, starts from the next scheduled hour, never immediately. Use Train now for an immediate run.
  • If the API was down at the run hour, the run happens once when it comes back, even after several missed days.
  • Indexes train one at a time. A failure is recorded on that index and doesn't stop the others.
  • Outcome: last_status is trained, skipped (thin traffic, busy or superseded) or error, and last_message holds the detail.
  • TRAINING_SCHEDULER_ENABLED=false keeps an API instance out of scheduling. Its schedules stay editable.
Known limit: if an instance dies mid-run, that day's status stays running until the next day's run. The run isn't retried the same day. Its lock is released automatically.

Learning tab

On each index's page (LearningTab.svelte):

  • Daily batch learning toggle, Learn from the last N days and Run at. The run hour is shown in UTC with your local time alongside.
  • Status: next run, last scheduled run (Trained, Skipped, Failed, Running or Never run) and the result message.
  • Train now: one immediate run with the current day window. It doesn't change the schedule. If a run is already in progress, it shows "already in progress".
  • The status refreshes every 30 s and when you return to the browser tab. A refresh never overwrites unsaved edits, and a response that a save overtook is ignored.

Concurrency

RaceHow it's prevented
Manual and scheduled runs overlapping, or two instances training the same indextrainer.train takes a per-index Postgres advisory lock. A second run returns "busy": 409 for a manual run, skipped for a scheduled one.
Two instances running the same scheduled runEach run is claimed with one conditional UPDATE, so exactly one instance wins.
Training exhausting the DB poolThe lock uses its own direct connection outside the shared pool, so a run holds at most one pool connection at a time. Even a 1-connection pool works.
A run that was in progress during a delete bringing the model backA per-index model generation, bumped by every publish and delete. A run publishes only if the generation is unchanged since it started, checked under a row lock.
A scheduled run starting after a deleteDELETE turns off the schedule and bumps the generation in one transaction. Scheduled runs also require the schedule to still be on, read with FOR SHARE until commit.
Turning a schedule off while a run is publishingThe same FOR SHARE lock: the change to "off" either commits first, and the run refuses, or waits until the publish is done.

A manual train after a delete is an explicit request and publishes normally.

Tests

  • Pure unit tests (tests/domain/query_boost/): clustering, scoring, serving (including the exact-title guard and magnitude guarantees), trainer orchestration, schedule timing, and the scheduler loop.
  • Real-Postgres tests:
    • model store round trip and snapshot reads
    • the schedule store, including five concurrent claims where exactly one wins
    • test_coordination.py, which pauses a real run halfway to reproduce each race above deterministically
  • Router tests: auth, 404, validation, the train → inspect → delete cycle, DELETE turning the schedule off, and the 409.
  • Frontend: helper tests (hour labels across time zones, refresh-merging, the latest-request gate) and a component test showing that leaving the tab mid-load leaks no polling.

What this doesn't do yet

  • Promotions only: a product shown often and never clicked gets 0, not a penalty.
  • Position handling is a decay curve, not IPS or a learned click model. Same follow-up as Case A.
  • No offline ranking metric (nDCG/MRR) yet. It's a mechanism, not a measured quality gain.
  • /v1/content search doesn't use post-RRF hooks, so it gets no learned boost.
  • Not learning-to-rank: a feature-based LTR model (GBDT or LambdaMART) is a later step that needs more traffic.
