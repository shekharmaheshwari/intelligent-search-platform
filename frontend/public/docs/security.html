Security & Secrets

How ISP stores and retrieves secrets, and the available authentication approaches.

Why not just use .env?

ISP uses a provider-based secret abstraction so the app code never changes when moving between environments. A single secrets.py module handles all secret access; the active backend is controlled by one env var (SECRET_PROVIDER).

Risk.env fileVault / Secrets Manager
Secrets on disk (EC2)Yes — plaintextNo
Stolen file = all secrets exposedYesNo — no key file to steal
Secret rotation after breachRe-deploy requiredChange value, done
Audit trail (who accessed what)NoneVault audit log / CloudTrail
Works offlineYesVault yes, AWS no

.env is kept as the env fallback for CI and minimal local setups only.

Provider architecture

At process startup bootstrap_secrets() is called in main.py before any other ISP import. It fetches all secrets from the active provider and injects them into os.environ. Everything else in ISP — config.py, routers, services — reads from os.environ as normal. Zero other code changes between environments. 

# main.py — bootstrap must run before any other ISP import
from isp.services.infra.secrets import bootstrap_secrets
bootstrap_secrets()

# safe to import everything else now
from isp.config import settings
from isp.routers import indexes, search, ...

Reads from .env file or shell environment.

Best for: CI pipelines, minimal local dev, quick prototypes.

vault Local

Best for: local dev parity with production.

Provider: vault (local Docker)

The isp-vault container runs on isp-net alongside the API. It uses file-backed storage with auto-init and auto-unseal on restart via vault/entrypoint.sh.

Configure backend

# backend/.env
SECRET_PROVIDER=vault
VAULT_ADDR=http://isp-vault:8200   # container name on isp-net
VAULT_TOKEN=isp-dev-token          # root token saved by entrypoint.sh

Populate secrets (one time, from your Mac)

export VAULT_ADDR=http://localhost:8200
export VAULT_TOKEN=isp-dev-token

# Enable KV v2 engine under the "isp" mount (one-time)
vault secrets enable -path=isp kv-v2

# Store all keys from _SECRET_KEYS — value field is mandatory in KV v2
vault kv put isp/TYPESENSE_API_KEY           value="your-typesense-key"
vault kv put isp/VOYAGE_API_KEY              value="your-voyage-key"
vault kv put isp/OPENAI_API_KEY              value="sk-..."
vault kv put isp/DATABASE_URL                value="postgresql+asyncpg://isp:pass@isp-db:5432/isp"
vault kv put isp/GOOGLE_SERVICE_ACCOUNT_JSON value='{"type":"service_account",...}'

How secrets.py reads from Vault

client = hvac.Client(
    url=os.getenv("VAULT_ADDR", "http://isp-vault:8200"),
    token=os.getenv("VAULT_TOKEN"),
)
try:
    # KV v2 automatically resolves isp/data/<key>
    secret = client.secrets.kv.v2.read_secret_version(
        path=key, mount_point="isp"
    )
    return secret["data"]["data"]["value"]
except Exception as e:
    log.warning("Vault: failed to read secret %s: %s", key, e)
    return ""

bootstrap_secrets() — the startup call

# bootstrap_secrets() skips keys already set in os.environ
# (so docker-compose ENV overrides always win)
def bootstrap_secrets() -> None:
    provider = os.getenv("SECRET_PROVIDER", "env")
    if provider == "env":
        return  # already in os.environ via .env file

    for key in _SECRET_KEYS:
        if os.environ.get(key):
            continue  # don't overwrite existing value
        value = get_secret(key)
        if value:
            os.environ[key] = value

Provider: aws (production)

In production on EC2, boto3 resolves AWS credentials automatically from the IAM Role attached to the instance — no credentials file on disk, no key to steal. 

# backend/.env (production EC2)
SECRET_PROVIDER=aws
AWS_REGION=us-east-1
# No access keys — IAM Role on the EC2 instance provides them automatically

Credential resolution order (boto3)

boto3.client("secretsmanager")
  │  checks in order:
  ├─ 1. AWS_ACCESS_KEY_ID + AWS_SECRET_ACCESS_KEY  (env vars — local dev)
  ├─ 2. ~/.aws/credentials                          (aws configure — local dev)
  └─ 3. IAM Role on EC2                             (metadata API — production)
        → temporary rotating token, nothing on disk

Populate secrets in AWS (one time)

aws secretsmanager create-secret --name isp/TYPESENSE_API_KEY \
  --secret-string "your-typesense-key"

aws secretsmanager create-secret --name isp/VOYAGE_API_KEY \
  --secret-string "your-voyage-key"

aws secretsmanager create-secret --name isp/OPENAI_API_KEY \
  --secret-string "sk-..."

aws secretsmanager create-secret --name isp/DATABASE_URL \
  --secret-string "postgresql+asyncpg://isp:pass@isp-db:5432/isp"

aws secretsmanager create-secret --name isp/GOOGLE_SERVICE_ACCOUNT_JSON \
  --secret-string '{"type":"service_account",...}'

IAM Role policy (minimum permissions)

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "secretsmanager:GetSecretValue",
    "Resource": "arn:aws:secretsmanager:us-east-1:*:secret:isp/*"
  }]
}

Authentication — Approach 3 implemented ★

OAuth2 / OIDC SSO is live. ISP uses Google (or GitHub) OAuth2 for admin access and per-index API keys for public search endpoints. Auth is off by default — set AUTH_ENABLED=true in backend/.env to activate it. No existing routes or handlers were modified.

How it works

Auth is implemented as a fully decoupled Starlette middleware (isp/auth/middleware.py) that is only registered when AUTH_ENABLED=true. Route protection follows a fixed priority order:

┌──────────────────────────────────────────────────────────────────┐
│                          ISP Backend                              │
│                                                                   │
│  OPTIONS (preflight)                       → always open          │
│  /health, /auth/*, /docs, /openapi.json    → always open          │
│                                                                   │
│  /v1/catalog/*, /v1/analytics/*,           → open (no auth)       │
│  /v1/intent/*, /v1/indexes/*/search/public   (PLP-facing routes)  │
│                                                                   │
│  All other /v1/*                           → OAuth2 JWT required  │
│  (indexes, rebuild, extensions, settings)    (Bearer header)      │
└──────────────────────────────────────────────────────────────────┘

Future: /v1/indexes/{id}/search/public and other PLP-facing routes will be protected by per-index API keys (X-Api-Key header). The api_keys table and management endpoints are already built — enforcement will be added once the API key UI is complete.

Login flow

1. User opens ISP → LoginGate.svelte checks localStorage for valid JWT
2. No token → "Sign in with Google" button → GET /auth/login
3. Backend redirects to Google consent screen (CSRF state in httpOnly cookie)
4. Google redirects to GET /auth/callback?code=...&state=...
5. Backend verifies state, exchanges code → fetches email + name from Google
6. Backend issues HS256 JWT (8h TTL) → redirects to http://localhost:3001?isp_token=<jwt>
7. LoginGate.svelte reads ?isp_token= from URL, stores in localStorage, cleans URL
8. All api.ts calls attach Authorization: Bearer <token>
9. On 401 → localStorage cleared → redirect to /auth/login

Enabling auth

Step 1 — Create OAuth credentials

For Google: open Google Cloud Console → Credentials, create an OAuth 2.0 Client ID (Web application), and add http://localhost:8001/auth/callback as an authorised redirect URI.

For GitHub: open GitHub → Settings → Developer settings → OAuth Apps, set the callback URL to http://localhost:8001/auth/callback.

Step 2 — backend/.env

AUTH_ENABLED=true
OAUTH_PROVIDER=google              # or github
OAUTH_CLIENT_ID=<from console>
OAUTH_CLIENT_SECRET=<from console>
OAUTH_REDIRECT_URI=http://localhost:8001/auth/callback
OAUTH_FRONTEND_URL=http://localhost:3001
OAUTH_ALLOWED_DOMAIN=yourcompany.com   # optional — restricts to one domain
JWT_SECRET=<random 32+ char string>

Step 3 — frontend/.env

PUBLIC_AUTH_ENABLED=true
PUBLIC_OAUTH_PROVIDER=google       # or github

Step 4 — restart

./deploy-api.sh

On next load the UI will show the login screen. The first successful sign-in stores an 8-hour JWT in localStorage.

JWT_SECRET must be at least 32 random characters and must never be committed to git. Generate one with: python3 -c "import secrets; print(secrets.token_hex(32))"

Disabling auth for local development

AUTH_ENABLED=false is the default. When it is false:

  • The AuthMiddleware is never registered — every route is open, identical to pre-auth behaviour.
  • LoginGate.svelte renders the app directly with no token checks or login screen.
  • api.ts does not attach an Authorization header and ignores 401 responses.

To turn auth off, either omit the variable entirely or set it explicitly in both files:

# backend/.env
AUTH_ENABLED=false

# frontend/.env
PUBLIC_AUTH_ENABLED=false

Then restart: ./deploy-api.sh. No code changes needed — the toggle is purely config.

Tip: Keep a backend/.env.local with AUTH_ENABLED=false for local dev and a backend/.env.prod with AUTH_ENABLED=true for production. Neither file should be committed to git.

API keys — infrastructure ready, enforcement coming

The API key system is fully built but not yet enforced. PLP-facing routes (/search/public, /catalog, /analytics, /intent) are currently open without any key. API key enforcement will be added in a future update once the key management UI is built.

What's already built

  • api_keys table in PostgreSQL — stores SHA-256 hashes, never plaintext
  • Management endpoints on the admin API (JWT required to call them):
# List keys for an index
GET  /v1/indexes/{id}/api-keys          Authorization: Bearer <admin-jwt>

# Create a key (plaintext returned once — copy it now)
POST /v1/indexes/{id}/api-keys          { "label": "PLP production" }
→ { "id": "...", "key": "isp_<48-hex-chars>" }

# Revoke a key
DELETE /v1/indexes/{id}/api-keys/{key-id}

What's coming

  • API key management panel in the ISP admin UI (per index)
  • Enforcement of X-Api-Key header on /search/public and optionally on catalog/analytics routes

Future: securing public routes with JWT

Currently /v1/catalog/*, /v1/analytics/*, /v1/intent/*, and /v1/indexes/{id}/search/public are open without any authentication. The planned approach to lock these down without breaking PLP or other consumers:

Option A — Per-index API keys (recommended)

Each external consumer gets a long-lived opaque key scoped to one or more indexes. The infrastructure is already built.

# Consumer sends one header — no OAuth flow required
POST /v1/indexes/{id}/search/public
X-Api-Key: isp_<48-hex-chars>
ProCon
No OAuth flow — works from curl, cron jobs, server-side appsKeys must be distributed and stored securely by each consumer
Per-index scope — PLP key cannot access admin routesRequires key management UI (planned)
Independently rotatable without touching admin credentials

What needs to be built: key management panel in the ISP admin UI; one-line change in middleware.py to re-enable the check.

Option B — Shared read-only JWT

Issue a single long-lived JWT (not tied to a Google account) that all consumers share. Simpler to distribute but harder to rotate and not scoped per-consumer.

# Generate once, distribute to consumers
POST /auth/service-token   { "label": "PLP service", "ttl_days": 365 }
→ { "token": "eyJ..." }

# Consumer sends as Bearer header
Authorization: Bearer eyJ...
ProCon
Single token, familiar Bearer patternAll consumers share the same secret — rotating affects everyone
No separate key management UI neededNo per-consumer or per-index scoping

What needs to be built: POST /auth/service-token endpoint; middleware to accept both admin JWT and service JWT on public routes.

Approach 1 — API Key / Password Gate

A single shared secret stored in .env. The frontend prompts for it on first load, exchanges it for a short-lived JWT, and attaches that JWT to every subsequent request.

User opens app
  → Frontend shows a password prompt
  → POST /auth/login { password }
  → Backend verifies against PASSWORD_HASH in .env, returns JWT
  → Frontend stores JWT in memory/localStorage
  → All API requests include Authorization: Bearer <jwt>
ProCon
Minimal moving partsSingle shared secret — no per-user identity
No external dependencyPassword rotation requires redeployment
Works offlineNot suitable for multi-user access control

Effort: ~1 day  |  Best for: solo operator or small team on a private network.

Approach 2 — Username + Password + TOTP

Traditional login form with an optional second factor — a 6-digit TOTP code from Google Authenticator or any TOTP app.

User opens app
  → Login form: email + password
  → POST /auth/login → returns { requires_totp: true }
  → Frontend shows TOTP input
  → POST /auth/totp/verify { code } → returns JWT
  → All API requests include Authorization: Bearer <jwt>

Requires: pyotp, passlib, python-jose, a users table in PostgreSQL.

ProCon
Per-user identity and audit trailRequires managing user accounts
Strong security with 2FARecovery flow needed if user loses authenticator
No external service dependencyMore backend surface to maintain

Effort: ~3–4 days  |  Best for: small teams wanting per-user identity without an external service.

Approach 4 — Managed Auth (Auth0, Clerk, Supabase)

Offload all auth to a hosted identity platform. Your backend only validates the JWT they issue.

ServiceFree tierNotes
Auth07,500 MAUMost feature-rich, supports SAML
Clerk10,000 MAUBest DX, Svelte SDK available
Supabase AuthGenerousGood if you later adopt Supabase DB
ProCon
Fastest to ship (~1 day, mostly config)External dependency — outage = login broken
MFA, social login, SAML out of the boxCost at scale, vendor lock-in
Admin dashboard for user managementUser data leaves your infrastructure

Effort: ~1 day  |  Best for: teams that need enterprise features without building them.

Approach 5 — SAML (Enterprise SSO)

The enterprise identity federation protocol used by Okta, Azure AD, and Google Workspace in SAML mode. Required when IT mandates corporate SSO.

User opens app
  → Backend generates SAML AuthnRequest → redirects to IdP (Okta, Azure AD)
  → User authenticates with corporate credentials
  → IdP posts signed SAML Assertion to /auth/saml/callback
  → Backend validates signature + attributes → issues JWT

SAML requires HTTPS — it will not work over plain HTTP. Plan for TLS termination (nginx / ALB) before implementing.

Effort: ~1 week  |  Best for: enterprise deployments where IT mandates Okta / Azure AD / ADFS.
